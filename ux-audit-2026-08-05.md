# UX Audit — SNAP

2026-08-05 · commit `4e6aeb5` · Source-only review of `src/` (24.3k LOC, 69 components, 15 routes) and the parts of `convex/` (10.1k LOC) that decide what the UI can show. No running instance was used, so nothing here is a claim about how the app looks or feels — visual questions are collected in §8.

---

## 1. What this app is

SNAP is a music-recognition game. You hear one second of a track, name it, and every extra second you wait costs points. It runs four modes off one engine: a **daily** challenge (five tracks, identical worldwide, one attempt, playable without an account), **ranked** 1v1 duels on an Elo ladder where the slower player takes health damage equal to the score gap, **practice** against rating-matched bots, and private **rooms** for 3–8 players. Progression is two parallel systems the code is careful to keep separate — Elo/rank (competitive standing) and XP/level (time invested), plus badges, streaks and a category-preference model.

The primary journeys, inferred from route structure and logic density: **(1)** stranger → landing → daily as guest → result → sign-up to save the score, which is the entire growth thesis and the only path an anonymous user has; **(2)** signed-in player → Play → queue → ban draft → duel → results, the retention loop, and where most of the code lives; **(3)** first sign-in → provisioning → onboarding modal → first match; **(4)** room create/join → invite by code → last-one-standing. The Play button is present on every screen on both form factors, and the app treats it as the one loud control — the dashboard deliberately isn't a launcher because of it.

**A note on calibration.** This is an unusually well-documented codebase: most non-obvious decisions carry a comment explaining what was tried before and why it was changed. Several findings below are cases where a fix was made in one place and an identical instance elsewhere was missed — I've cited the fixed version each time, because that's the pattern to copy rather than a design question to re-answer. Generic advice would be worthless here, so this report is short.

## 3. Fix — things that are broken or blocking

### 3.1 The queue entry has no failure state

**[S3] `Find a match` is fire-and-forget with no pending, disabled, or error state**
`src/app/ranked/hero.tsx` (`QueueControl`) · `src/app/queue-driver.tsx:323` · Designer lens

The button is `<Button size="lg" block onClick={queue.enqueue}>` with no `loading` prop, and `enqueue` is `() => void enqueueMutation({})`. Nothing awaits the mutation, nothing catches it, and nothing on screen changes until the `myQueueEntry` subscription round-trips back. If the mutation rejects — offline, a server error, an expired session — the rejection is swallowed by `void` and the screen is inert. The player has pressed the loudest control in the app and received no answer, so the reasonable read is "that didn't work", and the reasonable response is to press it again.

`queue.dequeue` (the Cancel button, `search-panel.tsx`) has the same shape. `queue.startBot` (`queue-driver.tsx:205-208`) is worse: it `await`s the mutation with no `try`/`catch` at all, so a failure is an unhandled promise rejection while the player looks at an unchanged "Play a bot instead" button.

This exact bug class was found and fixed one route over. `src/app/rooms/page.tsx:77-81` documents it: *"Both actions used to run bare — no pending flag, no disable, no catch. On a slow connection the page was visually inert between tap and route change, so the honest reading was 'that did not work' and a second tap made a second room."*

**Recommendation:** Give the three queue actions the treatment `rooms/page.tsx:82-108` already uses — an `async` handler with a pending flag driving `loading`, and a `catch` that surfaces a message. `enqueue` is the one that matters; it is on the critical path for the app's core mode. Component-level change, and the pattern is already written.

### 3.2 The daily's Start button can hang permanently

**[S3] A failed `daily.start` leaves the button spinning with no way out**
`src/app/daily/page.tsx:75-83` · Designer lens

```
async function begin() {
  setStarting(true);
  const result = await start({ guestToken: ensureGuestToken() });
  ...
  setStarting(false);
}
```

There is no `try`/`catch`. If `start` rejects, `setStarting(false)` never runs, the button stays in its `loading` state — which `ui/Button.tsx:91` also renders as `disabled` — and the only recovery is a page reload. The call site is `onClick={() => void onStart()}`, so the rejection is discarded and nothing is logged or shown.

This sits on the highest-traffic path in the product: the daily is the only mode playable without an account, and this is its single entry point. Every guest passes through this button.

A second, smaller issue in the same function: `start` can return `{ status: "already-played" }` (`convex/daily.ts:93`), and `setStatus` stores it, but the render only branches on `"catalogue-too-small"` — anything else falls through to the same `Landing`. In practice the reactive `myRun` query usually corrects the screen first, so this is a latent dead branch rather than a live bug, but it will surface as "pressing Start does nothing" the moment the timing goes the other way (two tabs, a slow subscription).

**Recommendation:** Wrap the body in `try`/`catch`/`finally`, reset `starting` in the `finally`, and render an error state near the button. Handle `already-played` explicitly rather than letting it fall through. A few lines.

### 3.3 A failed guess submission disappears silently

**[S3] `onGuess` has no error handling, so a dropped guess is indistinguishable from a slow one**
`src/game/RoundRunner.tsx:82-104` · Designer lens

`onGuess` awaits `submitGuess` and branches on `result.status`, but never catches. `GuessInput.submit` (`GuessInput.tsx:103-115`) wraps the call in `try`/`finally` — which correctly resets the `inFlight` ref — but has no `catch`, so the rejection propagates out of `submit`, which is invoked as `void submit(...)` from both the form's `onSubmit` and the suggestion buttons.

The player-visible result: the typed text stays in the field (it's only cleared inside the resolved branch), `feedback` is never set, and the round clock keeps running. There is no way to tell a guess that was rejected from one that never left the browser. This is a game scored on reaction time in tenths of a second, and the failure lands in the exact seconds where a player is least able to diagnose it.

The correct handling already exists a few files away, with a comment explaining the reasoning — `DuelMatch.tsx:144-156` on ban submission: *"Awaited BEFORE any optimistic UI change. Flipping state first is what left the old build stuck on 'Waiting for opponent…' with the error invisible."*

**Recommendation:** Catch in `onGuess` and set `feedback` to something honest and short ("Didn't send — try again"). Consider leaving the text in place on that path specifically, so the player can resubmit without retyping. `passRound` (`RoundRunner.tsx:226`) is fire-and-forget in the same way and deserves the same treatment. A few lines.

### 3.4 There is no error boundary, 404, or error route

**[S3] Any uncaught render error drops the player onto Next's default error page**
`src/app/` — no `error.tsx`, `global-error.tsx`, `not-found.tsx`, or `loading.tsx` at any level; no `componentDidCatch`/`getDerivedStateFromError` anywhere in `src/` · Designer lens

Every game screen is a client component subscribing to Convex queries, and several of those queries throw rather than returning null — `requireUser` throws for an identity with no user row. The codebase clearly knows this: it works around the hazard by hand in at least three places, each with a comment about the crash it prevents.

- `ranked/page.tsx:33-37` — *"Called above it, the query threw 'Not signed in' for every signed-out visitor."*
- `practice/page.tsx:59-61` — the same split, for the same reason.
- `queue-driver.tsx:92-102` — *"a query that throws takes the render down with it… gating on `isSignedIn` alone put a hard error on the first screen of every new player's first session — the one screen that has to work."*

Those three guards are correct. But they are manual, and there is nothing underneath them. Any future query added above a gate, any transient server error, any malformed document reaches Next's fallback: in production, an unstyled *"Application error: a client-side exception has occurred"* with no wordmark, no navigation, and no route back into the app. If it happens mid-duel the match is still live on the server, the presence heartbeat has stopped, and the player forfeits without ever being told what went wrong.

Separately, a mistyped URL gets Next's default 404 — the only screen in the product with none of its chrome.

**Recommendation:** Add `src/app/error.tsx` with the app's surfaces, a plain explanation, a reset button and a link home; and `src/app/not-found.tsx` in the same style. If a duel is recoverable after a client crash, say so on the error screen and link back to `/ranked` — the match state lives on the server, so it usually is. Two small files, and they contain a failure class the manual gates can only dodge one at a time.

### 3.5 A failed audio load silently costs the player the round

**[S2] The code states that a dead track must void the round; nothing implements it**
`src/game/useRoundAudio.ts:117` · `src/game/stages.tsx:1084-1099` · `convex/phases.ts:329-335` · Designer lens

`useRoundAudio.ts:117` is explicit about the requirement: *"A dead preview URL must void the round rather than penalise the player."* What actually happens is that `setError` is called and the error stays entirely client-side — nothing reports it to the server, and no mutation to void a round exists.

Meanwhile `GuessingStage` returns early on `audio.error !== null` (`stages.tsx:1084`), which means the whole lower block — the guess field *and* the Pass button — is never rendered. The player cannot guess, and cannot even concede. On the server, `phases.ts:329-335` scores an unsolved player 0 points with `elapsedMs: ROUND_DURATION_MS`, so the opponent wins the round and takes the full score gap as damage.

Net effect in a rated duel: a CDN hiccup or a browser autoplay block costs a round, HP, and — if it lands late in a close match — the match and the rating. The screen says *"This track took too long to load. The round moves on shortly"*, which reads as a minor inconvenience rather than a loss the player just took.

Two of the three error causes are recoverable in principle: `playback-blocked` (`:196`, `:234`, `:301`) is an autoplay-policy rejection that a tap would clear, and `audio-timeout` (`:137`) is an 8-second deadline that a slow connection may beat on retry. Neither is offered a retry.

**Recommendation:** Two changes, separable. Short-term: render the Pass control in the error state so the player can close their own round, and add a "Try again" that re-issues `audio.load()` and clears the error — the per-round reset at `:97` already handles clearing correctly. Longer-term, if the fairness matters: report the failure to the server and have `resolveRound` treat a reported audio failure as a no-damage round for that player. That's a real design decision with an abuse surface (a client can claim failure to dodge a losing round), so it's worth deciding deliberately rather than defaulting.

### 3.6 The onboarding modal does not contain focus or lock scroll

**[S2] The one dialog that blocks the whole app is the one that isn't a `Dialog`**
`src/app/onboarding.tsx:88-98` vs `src/ui/Dialog.tsx:7-20` · Designer lens

`ui/Dialog.tsx` exists specifically to stop this, and its own doc comment names onboarding as one of the three copies it was extracted from: *"the pattern had been hand-rolled three times — onboarding, the report dialog, and now auth — and each copy got a slightly different subset of the behaviour right. The parts that are easy to forget and impossible to notice missing are the ones that live here."* The report dialog and auth were migrated (`u/[handle]/report.tsx`, `auth/AuthDialogButton.tsx`, `game/LeaveMatch.tsx`). Onboarding still renders its own `fixed inset-0 z-50` overlay with `role="dialog" aria-modal="true"` and none of the behaviour.

What's missing, concretely: focus is never moved into the panel on open, so a keyboard or screen-reader user arriving at their first-ever screen starts at the top of a document that is visually behind a blur; there is no scroll lock, so the page slides under the overlay; and `<AppShell>` is a sibling in `layout.tsx:85-90` with no `inert` or `aria-hidden`, so every nav link and the whole dashboard behind the modal remains in the tab order. `aria-modal="true"` tells assistive tech the background is inert while the DOM says otherwise.

Escape-to-close and backdrop-dismiss are correctly *absent* here — this is a blocking gate and must not be dismissible — which is the one real reason not to drop `Dialog` in unmodified.

**Recommendation:** Either add an `dismissible={false}` (or `blocking`) prop to `Dialog` and use it here, or lift the focus-in / focus-return / scroll-lock effect out of `Dialog.tsx:43-70` into a shared hook both call. Also mark the shell `inert` while the gate is up, which is now a single attribute in all current browsers. Component-level change.

## 4. Improve — things that work but are weak

### 4.1 Every route has the same page title

**[S2] `layout.tsx` is the only metadata export in the app**
`src/app/layout.tsx:47-58` · IA lens

No route segment exports `metadata` or `generateMetadata`. Every screen — `/daily`, `/ranked`, `/leaderboard`, `/rooms`, `/settings`, `/u/[handle]`, `/m/[matchId]` — renders with `<title>SNAP</title>`.

Consequences, in rough order of cost:

- **Shared links don't describe what was shared.** `metadataBase`, an `opengraph-image.tsx` and Twitter card config are all in place (`layout.tsx:34-57`) — the infrastructure for good previews exists. But a player sharing their profile or a match posts a link that previews as "SNAP — One second of a song. Name it before they do." A profile link that said `@handle — Gold II · 1,240` would carry the ladder into the share, which is the mechanism this genre grows on.
- **Browser history is unusable.** Every entry reads "SNAP", so a player cannot get back to the leaderboard they were looking at ten minutes ago except by navigating.
- **Multiple tabs are guesswork** — plausible in a game where you queue on one tab and read the ladder on another, which the app explicitly supports.
- It also fails WCAG 2.4.2 Page Titled.

There's a specific irony worth flagging: `queue-driver.tsx:283-313` spends a careful paragraph on restoring the correct title after a search ends, keyed per route because *"the right thing to put back is whatever this route calls itself"*. Every route calls itself the same thing, so that mechanism currently restores one constant string.

**Recommendation:** Add `export const metadata` to each static route (a line each), and `generateMetadata` to `/u/[handle]` and `/m/[matchId]` — those two are where the sharing value is. Keep the `title.template` in the root so everything ends up `Ladder — SNAP`. Roughly a line per route plus two small async functions.

### 4.2 Three relative-time formatters that disagree

**[S2] The same match reads "2 hours ago", "today" and "Today" depending on which screen you're on**
`src/app/dashboard/last-result.tsx:19-33` · `src/app/u/[handle]/page.tsx:465-472` · `src/app/m/[matchId]/page.tsx:101-111` · IA lens

Three independent implementations with three different behaviours:

| | granularity | casing | ≥30 days |
|---|---|---|---|
| `last-result.tsx` (dashboard, rooms list) | "just now" → minutes → hours → days | lowercase `yesterday` | months |
| `u/[handle]` (profile history) | days only | lowercase `today` | `3 Aug` — **no year** |
| `m/[matchId]` (match detail) | days only | capitalised `Today` | `3 Aug 2025` |

The match-detail one carries the comment *"Matches the history list"* — it doesn't, in either granularity or casing.

The consequence a player actually hits: a duel finished 90 minutes ago is "2 hours ago" in the dashboard's recent-matches strip, "today" on their profile, and "Today" on the match page — three renderings of one event across three screens they move between freely. And a match from over a year ago shows as `3 Aug` on the profile with no year, which is genuinely ambiguous once an account has more than twelve months of history.

**Recommendation:** `last-result.tsx`'s version is the most complete; export it from a shared module (`src/engine/` or `src/ui/`) and delete the other two. Add the year to the fallback branch. Small change, and it removes a class of drift rather than one instance.

### 4.3 `Copy result` gives no feedback when it fails

**[S2] The failure branch sets state to the value it already had**
`src/game/DailyResult.tsx:170-184` · Designer lens

```
try {
  await navigator.clipboard.writeText(shareText);
  setCopied(true);
} catch {
  setCopied(false);
}
```

`copied` is already `false` on the first attempt, so the catch changes nothing on screen — the button still reads "Copy result" and the player has no idea whether anything happened. `writeText` rejects on an insecure origin and under a denied clipboard permission, both of which are real for a link opened in an in-app browser.

This matters more than it looks because of what's above it: `Share` only renders when `navigator.share` exists (`:155`), which is a mobile capability. On desktop, `Copy result` is the *only* route to the shareable grid — and sharing the grid is, per the component's own comment, the reason the daily exists (*"the reason to finish it is to send the grid to someone"*).

The comment on that catch block says the previous version's rejection *"went nowhere with no feedback at all"*. The unhandled rejection was fixed; the missing feedback wasn't.

The correct pattern is already in the codebase, at `src/app/rooms/[code]/page.tsx:310-319`, which tracks a `failed` state and renders *"Copy failed — select the code"* — telling the player both that it failed and what to do instead.

**Recommendation:** Copy the rooms pattern exactly: a `failed` state, and a message that names the fallback (the text is on screen and selectable). Also reset `copied` on a timer — it currently latches to "Copied" forever, so a second copy attempt gives no confirmation. A few lines.

### 4.4 Three mute controls, three accessible-name strategies

**[S1] Two of them announce a state that contradicts their own label**
`src/ui/MuteToggle.tsx:20-31` · `src/app/settings/page.tsx:201-207` · `src/app/app-shell.tsx:708-713` · Designer lens

| Control | Name when muted | `aria-pressed` |
|---|---|---|
| `MuteToggle` (shell, match chrome) | "Unmute sound effects" | `true` |
| Settings `SoundSection` | "Unmute" (visible text) | `true` |
| `UserMenu` menu item | "Sound off" | absent |

The first two announce as *"Unmute sound effects, toggle button, pressed"* — the name describes the action available, the state describes something else, and together they say the un-mute is switched on while the sound is off. The third is a menuitem that states the current state and toggles it, with no pressed semantics at all.

`app-shell.tsx:883-885` states the right rule for exactly this situation, about the mobile Play button: *"The name stays put and the STATE moves — that is what `aria-expanded` is for. Renaming the control to 'Close…' on open makes it a different thing to anyone listening, and breaks every locator that refers to it by name."*

**Recommendation:** Apply that rule. Fix the name to "Sound effects" on both toggle controls and let `aria-pressed` carry the state — which also stabilises the test locators. The menu item is a different control type and is fine as it is. Small change across three files.

## 5. Remove — things that should be cut

### 5.1 Onboarding collects "Favourite genres" that nothing reads

**[S2] A whole fieldset in first-run setup whose answer is written and never used**
`src/app/onboarding.tsx:188-219` · `convex/users.ts:298` · `convex/schema.ts:123` · Researcher lens

The onboarding modal renders a toggle for every category under the legend "Favourite genres — optional". The selection is passed to `completeOnboarding`, which writes `preferredCategoryIds` to the user row. Grepping every read of that field across `convex/` and `src/` returns only the two writes (`users.ts:298`, `users.ts:343`) and the schema declaration. Nothing reads it: not matchmaking, not `ensureChallenge`, not the veto pool, not track selection, not the profile card, not the dashboard's `Categories` panel (which reads `categoryRatings` — measured performance, a different thing entirely).

So the app asks a new player to declare their taste at the single highest-stakes moment in the funnel, and discards the answer. Two costs: the obvious friction on a screen whose own comment says *"nobody should be blocked from playing by a form"*, and an implied promise — a player who picks four genres has been told, reasonably, that the game will use them.

**Recommendation:** Decide which way, and do it now rather than leaving it ambiguous. If preferences are meant to shape the veto pool or track weighting, that's a real feature and this data is already being collected for it. If not, delete the fieldset — it is the largest block in the modal and the least load-bearing. Either is a small change; the decision is the work.

**Not a removal, but noted:** `convex/ranked.ts` `queueStatus` reads as dead — it was superseded by `myQueueEntry` + `queueSize` — but `ranked.ts:81` documents it as a deliberate compatibility shim for browsers on the previous deploy. Correct call; worth a calendar reminder to delete it once those clients have drained, since nothing in the code will surface when that's true.

## 6. Add — things that are missing

### 6.1 There is no instrumentation at all

**[S3] Zero analytics events in the entire codebase**
Whole codebase · Researcher lens

Searching `src/` and `convex/` for `analytics`, `posthog`, `mixpanel`, `amplitude`, `gtag`, `logEvent`, `@vercel/analytics`, and any custom `track(` wrapper returns nothing. There is no `console.error` either. Nothing measures anything, and nothing records failures.

This matters most because of what the product is betting on. The landing page, the guest token system (`src/app/guest.ts`), the run-claiming flow (`app-shell.tsx:1099-1112`) and the `SaveScore` panel (`DailyResult.tsx:210-262`) together constitute a carefully built guest→signup funnel — the app's entire growth mechanism, with real engineering behind it. Its conversion rate is currently unknowable. Each of the following questions has a design decision already made against it, and no way to check the answer:

| Question | The bet already made | Currently measurable? |
|---|---|---|
| What share of guests who finish the daily sign up? | The whole `SaveScore` panel and its "restate the score" copy | No |
| Do players abandon the daily mid-run, and on which song? | `DAILY_SONGS = 5`, no mid-run save prompt | No |
| How long do players wait before cancelling the queue? | `BOT_FALLBACK_MS`, the bot-offer timing | No |
| Do players complete onboarding or bounce off it? | A four-field modal on first sign-in | No |
| How often does audio actually fail? | §3.5 is only worth fixing if the rate is non-trivial | No |
| Which modes retain, and which are ballast? | Six nav destinations, two of them demoted by hand | No |

**Recommendation:** Install one lightweight product-analytics client and instrument the guest funnel first — `daily_start`, `daily_round_complete` (with the round index), `daily_finish`, `save_score_shown`, `save_score_clicked`, `signup_complete`, `guest_run_claimed`. That is seven events and answers the most valuable open question in the product. Add `queue_enqueue` / `queue_cancel` with elapsed ms, and an `audio_error` event carrying the reason, second. Deliberately not a large project: the events above are all at call sites that already exist.

### 6.2 Bio and genres cannot be edited after onboarding

**[S2] `users.updateProfile` handles all three profile fields and has no caller**
`convex/users.ts:307-345` · `src/app/settings/page.tsx` · Designer lens

Settings offers exactly three things: picture, username, sound. `updateProfile` — which takes `bio`, an avatar colour and `preferredCategoryIds`, validates the bio against the blocklist, and enforces the avatar rules — is called from nowhere in `src/`.

So a tagline written during first-run setup is permanent. This is precisely the gap the settings page's own header comment describes for the username: *"Wires `users.setHandle`, which existed with no caller — meaning the username chosen during onboarding was permanent for no reason other than a missing screen."* The same sentence is now true of the bio, one file away.

It's sharper than a missing convenience, because of what else touches the bio. `src/app/u/[handle]/report.tsx` lets any player report someone's bio; enough reports set `bioHidden` (`schema.ts`, `REPORTS_TO_HIDE_BIO`). So a player can have their tagline hidden pending review for being inappropriate, and has no way to change the thing they're being penalised for. The only recovery path is a support request to someone with database access.

**Recommendation:** Add a `BioSection` to settings alongside `HandleSection` — same `Field` + `Input` + save-with-error pattern, pointed at `updateProfile`. If §5.1 resolves toward keeping genres, they belong in the same section. One new section in a file that already has two examples of the pattern.

## 7. Research gaps — what you're deciding without evidence

### Assumptions with no supporting evidence

1. **That a guest who finishes the daily will convert.** The entire guest system — token management, server-side one-run-per-day for anonymous players, run claiming on sign-in — exists to serve a conversion moment (`DailyResult.tsx:210`). If the conversion rate is near zero, that machinery is carrying the cost of an unvalidated hypothesis, and the answer would probably be a different ask (email the result? a streak that only persists with an account?) rather than better copy on the same panel. **Cost if wrong:** the growth strategy is unfounded and the effort is misallocated.

2. **That the ban draft is understood.** The draft is a 15-second turn-based phase (`VETO_PHASE_MS`) with a screen of its own and copy — *"Take away something they are good at"* — that assumes a player already knows which categories their opponent is good at. Nothing on that screen shows the opponent's category ratings. **Cost if wrong:** a mandatory phase in every rated match is a coin flip players click through, and it delays every duel by fifteen seconds.

3. **That the two-currency progression is legible.** `app-shell.tsx:554-565` documents the design intent carefully — Elo is standing, XP is time invested, and they're deliberately separated because *"the old footer printed `1000 · L4` on one line and invited exactly the confusion that implies."* The separation is a design fix for a suspected confusion; whether players now hold the distinction is untested. **Cost if wrong:** the level bar is decoration and the rank is the only thing carrying motivation.

4. **That the daily's mobile landing carries enough to convert a stranger.** `landing.tsx:76` and `:183` hide both the feature row and the entire `Rules` section below `sm`, deliberately (they stay in the HTML for crawlers). On a phone — the daily's primary device — a first-time visitor sees a headline, one paragraph, and the challenge card. **Cost if wrong:** the highest-traffic version of the front door is the one that explains the game least.

5. **That "Practice" reads as low-stakes rather than second-class.** It has been demoted twice, deliberately and with comments (`ranked/page.tsx:95-97`, `app-shell.tsx:941-943`), from a card to one sentence, and from a tab to a menu item. That's a considered ranking of ranked over practice — but for a nervous new player, practice is the on-ramp, and it is now the least visible mode in the app.

### Instrumentation gaps

Everything in §6.1. In priority order, the four events that would settle the most: `daily_finish` → `save_score_clicked` → `signup_complete` (assumption 1); a per-step onboarding event (whether the modal is a wall); `queue_cancel` with elapsed ms (whether `BOT_FALLBACK_MS` is tuned right); `audio_error` by reason (whether §3.5 is a rare edge or a routine tax).

### Worth actually testing

1. **Does a first-time player understand what the ban draft is asking?** Five-participant moderated test, first ranked match, think-aloud through the draft only. Watch for: do they read the category names, do they ban confidently or randomly, can they say afterwards what they took away and why. Would settle assumption 2, and tell you whether the draft needs the opponent's category strengths on screen. ~1 day.
2. **Where do guests drop out of the daily?** Funnel analytics, not a study — but it needs §6.1 first. The instrumentation is a prerequisite for almost every other question here, which is why it ranks above the qualitative work.
3. **Is the rank/level distinction held after a few matches?** Five-participant comprehension check: after their third match, ask what their rating is, what their level is, and what makes each go up. Cheap (15 minutes each, can be unmoderated with open text) and would settle assumption 3 outright.

### Evidence that does exist

Not zero, and worth naming. The E2E suite (`e2e/`, Playwright) encodes real user flows as executable assertions, and some carry UX contracts directly — `guest-daily.spec.ts` asserts the daily route never uses duel vocabulary (`daily/page.tsx:33-36`), and several specs pin accessible names so a rename can't silently break a locator. `src/app/design/gallery.tsx` is a fixture-driven harness rendering every rare state — audio failures, all eight guess-rejection reasons, draws, forfeits, empty boards — which is a genuine substitute for the states you cannot reach by playing. That's a stronger evidence base than most products this size have; it just isn't measuring live behaviour.

## 8. Needs visual confirmation

Flagged from code, not judgeable from source:

- **The `/ranked` hero's one-screen contract.** `hero.tsx:157-185` derives a height budget of `100dvh - 8.5rem` from the mobile chrome, and the whole composition depends on that arithmetic holding. Worth checking on a 360×640 device that the Find-a-match button and, while searching, Cancel are both above the fold in every state — including a Legend-tier emblem, which is the tallest case.
- **The searching panel's `min-h-[16.5rem]` floor** (`search-panel.tsx`) is a measured value meant to stop Cancel sliding under a finger when the fallback branch swaps in. Check that the panel genuinely doesn't move at the `fallingBack` transition.
- **Colour contrast of the tier accent colours on `ink` backgrounds.** Rank labels are rendered in `rank.tier.accent` at display sizes (`hero.tsx:283-288`). `Input.tsx:9-12` shows the team already reasons about the 3:1 non-text threshold, so the tokens are probably considered — but per-tier accent-on-background pairs need measuring, especially the bronze and silver ends.
- **The waveform's locked/unlocked distinction** (`game/Waveform.tsx`) carries real information — how much of the clip you have — through a colour and opacity difference on thin bars. Worth checking it survives a bright phone screen outdoors, and that it isn't the only channel carrying that information.
- **Whether the `Beat`-staged entrance animations read as polish or delay** on the dashboard, which stages seven groups in sequence (`hub.tsx`). Reduced-motion is handled; the full-motion default is a feel question.
- **The collapsed sidebar rail at 64px** — whether the glyph-only nav is identifiable without the `title` tooltip.

## 9. What's working well

Genuinely, and worth naming because several of these are patterns to extend to the places that lack them:

- **`LeaveMatch.tsx` is the best-considered component in the app.** Per-mode consequence copy that states the cost plainly rather than softening it, a `beforeunload` guard, and a history sentinel that converts a Back press into the same confirm — solving a case (*"Backing out used to unmount the match silently, which stopped the presence heartbeat and forfeited the duel with no indication that anything had happened"*) that most products never notice.
- **Failure-path handling in `practice/page.tsx:117-137` and `rooms/page.tsx:82-108`** is exactly right — pending flags, disabled controls, caught errors, and player-facing messages that don't leak implementation (*"The old copy told them to run `npm run seed-bots` — a developer instruction shipped to players"*). These are the templates §3.1–3.3 should be brought up to.
- **`src/app/guest.ts`** states precisely what the guest token does and does not prevent, and declines to fingerprint. The UI copy is then written to match that honesty rather than overclaiming.
- **The design gallery and the dev-route gating.** `/design` and `/admin` both `notFound()` in production (`design/page.tsx:18`, `admin/page.tsx:14`) — no dead weight, and the gallery is a real answer to "how do you review states you can't reach by playing".
- **`GuessInput.tsx`** is a correct ARIA 1.2 combobox — `aria-activedescendant`, `aria-expanded`, `aria-controls`, arrow-key handling, `onMouseDown` preventDefault to protect focus, suggestions above the field so the on-screen keyboard doesn't cover them, and a local index so the list isn't a round-trip behind the typing.
- **Loading and empty states are handled nearly everywhere**, and the distinction between `undefined` (still asking) and `null`/empty (nothing there) is respected explicitly, with comments at `daily/page.tsx:88-95` and `practice/page.tsx:69-74` describing the bug each guard prevents.
- **Accessibility fundamentals are well above average**: no `onClick` on non-interactive elements anywhere, a global `:focus-visible` rule, `aria-busy` on loading buttons, labelled `Meter` components for HP and XP, `role="alert"` on guess feedback, `min-h` values chosen against the 44px touch target, `prefers-reduced-motion` respected throughout, and `nav`/`main`/`header` landmarks with `aria-label="Main"` on both nav instances.
